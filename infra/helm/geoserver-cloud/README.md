# GeoServer Cloud OpenShift Helm Chart

This chart deploys the Node OIDC edge proxy, GeoServer Cloud services, GeoServer
ACL, and RabbitMQ into an existing OpenShift namespace. PostgreSQL/PostGIS is
owned by the separate `infra/helm/crunchy-postgres/` chart. The proxy is the only
chart-managed public edge; the GeoServer gateway stays on an internal ClusterIP
Service. This is a parallel deployment path. It does not change the Azure
Container Apps Terraform stack, Azure Key Vault, Azure Container Registry,
Python catalog-as-code, or GitHub Actions workflows.

## Platform prerequisites

The namespace owner must provide:

- An OpenShift namespace with quota, LimitRange, and an approved storage class.
- The Crunchy Postgres Operator and its CRDs, installed before this chart through
  the separate Crunchy chart.
- The BC Gov Platform Artifactory pull path and an image-pull Secret. The default
  `docker-remote` name is a platform-console value and MUST be changed if the
  target cluster uses another Docker Hub remote repository name.
- By default, the chart creates `<geoserver-release>-runtime` for RabbitMQ,
  GeoServer admin, ACL, and proxy credentials (`geoserver-cloud-runtime` for
  the default release). Set `secrets.runtime.name` only when a different
  stable Secret name is required. It generates values on first install and
  preserves them on upgrade by reading the existing Secret. Do not delete this
  Secret during an application upgrade or rollback.
- A process to register the generated `oidc-client-secret` with the configured
  OIDC provider before users sign in.
- A published `node-oidc-proxy` image in the approved Artifactory local
  repository. The chart does not build or push application images.
- An approved pgBackRest backup storage class and a tested restore procedure.
- An optional approved off-cluster S3-compatible pgBackRest repository. When
  enabled, provide its endpoint, bucket, access key, and secret key through the
  Crunchy values. The Crunchy chart creates the release-scoped S3 Secret.
- RabbitMQ PVC storage is capped at `1Gi` (1024Mi); larger values are rejected
  by the chart schema.
- RabbitMQ is intentionally a single warm broker, matching the Azure Container
  Apps design. Do not raise `rabbitmq.replicas` without adding and validating a
  real RabbitMQ clustering and peer-discovery design.

The BC Gov platform provides two supported image-pull patterns:

1. Use the cluster-wide remote-cache Secret. The project-set Secret is commonly
   named `artifactory-creds`.
2. Create an `ArtifactoryServiceAccount` in the `-tools` namespace or the
   platform-approved namespace. Archeobot creates a Secret named like
   `artifacts-<name>-<random>`. Link that Secret to the relevant service accounts
   and keep the explicit `global.imagePullSecrets` reference in the rendered
   workloads:

```powershell
oc secrets link default <pull-secret-name>
oc secrets link builder <pull-secret-name>
```

For Gold DR, synchronize the generated Secret according to the platform process.
The Crunchy dependency does not expose a parent-chart `imagePullSecrets` value for
the operator-created database pods, so the cluster-wide pull Secret or service
account link must also cover those pods.

## Image paths

Docker Hub-origin GeoServer Cloud, ACL, RabbitMQ, and PostgreSQL initialization
images render as:

```text
artifacts.developer.gov.bc.ca/<docker-hub-remote>/<image>:<immutable-tag>
```

Crunchy Postgres uses the BC Gov local repository:

```text
artifacts.developer.gov.bc.ca/bcgov-docker-local/crunchy-postgres-gis:ubi9-18.1-3.6-2547
```

The project-built proxy image uses the approved Artifactory local repository:

```text
artifacts.developer.gov.bc.ca/bcgov-docker-local/node-oidc-proxy:<immutable-tag>
```

Build and publish that image through the approved platform process before the
Helm install. Override `images.proxy.tag` only with a pinned tag or digest.

Confirm the Docker Hub remote repository name in the Artifactory console before
installation, then override it in the environment values file. Direct `docker.io`
references and the `latest` tag are rejected by both the values schema and the
chart validation helper.

## Secrets

The chart creates the application runtime Secret. The default keys are:

| Secret | Keys | Consumer |
| --- | --- | --- |
| `<geoserver-release>-runtime` | `rabbitmq-username`, `rabbitmq-password`, `geoserver-admin-username`, `geoserver-admin-password`, `acl-admin-password`, `acl-geoserver-password`, `acl-geoserver-password-plain`, `oidc-client-secret`, `session-cookie-secret`, `rabbitmq-erlang-cookie` | All application workloads |
| `<crunchy-release>-pguser-<crunchy-user>` | `dbname`, `port`, `user`, `password` | Generated by Crunchy Postgres; default user is `geoserverproxy` |

The runtime Secret values are generated by Helm and are not committed to values
files. Retrieve the generated OIDC client secret through the approved operator
process and register it with the OIDC client. The database Secret remains owned by
Crunchy, and `global.imagePullSecrets` remains owned by the platform registry
process. Helm release metadata contains the rendered Secret manifest, so restrict
access to Helm release storage and use the platform's approved secret backup and
rotation process.

For an operator-controlled OIDC client registration, retrieve only the client
secret value with:

```powershell
oc get secret geoserver-cloud-runtime -n geoserver-dev `
  -o jsonpath='{.data.oidc-client-secret}' | %{ [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($_)) }
```

The separate Crunchy chart creates the generated PostgreSQL user Secret. Do not
create a competing Secret with that name. Set `database.crunchyReleaseName` to
the Crunchy Helm release name. Application JDBC and PostgreSQL clients then use
`<crunchy-release>-pgbouncer:5432`. The deployment script waits for the
operator-created Secret and pgBouncer Service before it installs this chart.

## Validate and render

Run these commands before cluster mutation:

```powershell
helm lint infra/helm/crunchy-postgres --strict `
  -f infra/helm/crunchy-postgres/values/values-dev.yaml
helm template crunchy-postgres infra/helm/crunchy-postgres `
  --namespace geoserver-dev `
  -f infra/helm/crunchy-postgres/values/values-dev.yaml `
  > rendered-crunchy-dev.yaml
helm lint infra/helm/geoserver-cloud --strict `
  -f infra/helm/geoserver-cloud/values/values-dev.yaml
helm template geoserver-cloud infra/helm/geoserver-cloud `
  --namespace geoserver-dev `
  -f infra/helm/geoserver-cloud/values/values-dev.yaml `
  --set-string database.crunchyReleaseName=crunchy-postgres `
  > rendered-geoserver-dev.yaml
& infra/helm/geoserver-cloud/scripts/validate.ps1 `
  -ValuesFile infra/helm/geoserver-cloud/values/values-dev.yaml `
  -CrunchyReleaseName crunchy-postgres `
  -RequireProxy -RequireRuntimeSecret
```

Both validators require `kubeconform` in `PATH`. On macOS or Linux, install it
and run the cross-platform validator:

```bash
infra/helm/geoserver-cloud/scripts/validate.sh \
  infra/helm/geoserver-cloud/values/values-dev.yaml
```

On Windows, install the same tool and run the PowerShell validator. It performs
the same strict Kubernetes schema check as the Bash validator:

```powershell
infra/helm/geoserver-cloud/scripts/validate.ps1 `
  -ValuesFile infra/helm/geoserver-cloud/values/values-dev.yaml `
  -CrunchyReleaseName crunchy-postgres `
  -RequireProxy -RequireRuntimeSecret
```

Review the Crunchy render for the `PostgresCluster`, pgBackRest resources, and
operator-owned release name. Review the GeoServer render for Artifactory image
paths, `imagePullSecrets`, the OIDC proxy Deployment and Service, the internal
gateway Service, probes, PDBs, HPAs, and release-derived pgBouncer/Secret names.
Enable only the proxy Route with an approved hostname and TLS policy. Never enable
a direct gateway Route.

Set these non-secret values for the target environment before installation:

- `proxy.oidc.issuer`
- `proxy.oidc.clientId`
- `proxy.publicOrigin`
- `proxy.route.host` when `proxy.route.enabled` is true
- `images.proxy.tag`

The base values intentionally leave the public host empty so a deployment
cannot silently use another environment's OIDC callback. Every environment
values file must set both `proxy.publicOrigin` and `proxy.route.host` to the
same approved host. The development example uses
`eo-dmi-geoserver-dev.apps.silver.devops.gov.bc.ca`.

Supply the OIDC client secret on the terminal for the first install. Helm stores
the rendered Secret in release metadata, so do not place the value in a committed
values file. Use the deployment script. PowerShell:

```powershell
$env:OIDC_CLIENT_SECRET = Read-Host "OIDC client secret"
bash infra/helm/deploy-geoserver-cloud.sh `
  --namespace geoserver-dev `
  --environment dev `
  --crunchy-release crunchy-postgres
Remove-Item Env:OIDC_CLIENT_SECRET
```

Bash:

```bash
read -r -s OIDC_CLIENT_SECRET
export OIDC_CLIENT_SECRET
infra/helm/deploy-geoserver-cloud.sh \
  --namespace geoserver-dev \
  --environment dev \
  --crunchy-release crunchy-postgres
unset OIDC_CLIENT_SECRET
```

The explicit value is used only when the runtime Secret does not already exist.
On later upgrades, the existing Secret is preserved. To rotate the client secret,
update the OIDC provider and replace the runtime Secret through the approved
operator procedure before restarting the proxy.

The WPS profile intentionally sets `ACL_ENABLED=false` and omits the ACL Spring
profile because WPS and GeoServer ACL integration is not supported by the current
GeoServer Cloud topology.

With an authenticated OpenShift context, use the deployment script. It installs
Crunchy first, waits for the generated Secret and pgBouncer endpoints, then
installs GeoServer:

```bash
OIDC_CLIENT_SECRET="${OIDC_CLIENT_SECRET:-}" \
  bash infra/helm/deploy-geoserver-cloud.sh \
  --namespace geoserver-dev \
  --environment dev \
  --crunchy-release crunchy-postgres
```

The script is the required ordering mechanism. Do not use a single Helm release
for both charts. With an authenticated OpenShift context, run the server-side
admission checks after the script's two renders:

```powershell
oc apply --dry-run=server -f rendered-geoserver-dev.yaml
```

This catches restricted-v2 SCC, quota, image-policy, CRD, and storage errors. The
chart does not create namespaces, NetworkPolicies, Routes other than the optional
proxy Route, or cluster-scoped RBAC. NetworkPolicy ownership remains with the
platform namespace baseline. That baseline must allow the approved Route to reach
`oidc-proxy`, the proxy to reach `gateway`, application Services to reach pgBouncer
and RabbitMQ, and the database-init Job to reach pgBouncer.

The application Service and Deployment names are intentionally fixed to
`gateway`, `webui`, `wms`, `wfs`, `wcs`, `wps`, `rest`, `gwc`, `acl`,
`oidc-proxy`, and `rabbitmq` because the gateway topology uses those names as
stable DNS targets. Two releases cannot coexist in one namespace. Use separate
namespaces for parallel environments or release tests.

The local Helm validator cannot prove server-side SCC admission, arbitrary-UID
image behavior, or the configured actuator paths against running containers. The
server-side dry run and the dev install smoke checks remain mandatory promotion
gates; tasks 8.3 through 8.5 are intentionally open until an approved cluster
context is available.

## Post-deploy security configuration

`deploy-geoserver-cloud.sh` automatically runs
`infra/helm/configure-geoserver-security.sh` after a successful GeoServer
install/upgrade. It wires GeoServer's `sec-username`/`sec-roles`
pre-authentication header (injected by the Node OIDC proxy and gateway) into
GeoServer's own security filter chains.

This step exists because GeoServer never reads that header on its own:
GeoServer Cloud's `environment-admin-auth`/`gateway-shared-auth` extensions
only provide the *capability* for header-based pre-authentication, they do
not create a filter for it. Without this step, `sec-username` arrives at
every backend correctly but nothing reads it, so an otherwise-successful OIDC
login is silently treated as anonymous — the logged-in user's name and
Logout link simply never appear in the UI.

The step is idempotent (safe on every deploy) and non-fatal (a failure here
is logged as a warning, not a script failure, since the application
deployment itself already succeeded by that point). Skip it with
`--skip-security-config`, or bootstrap an initial `ROLE_ADMINISTRATOR`
principal with `--admin-principal you@gov.bc.ca`. It can also be re-run
standalone at any time, including against an environment that predates this
step:

```bash
infra/helm/configure-geoserver-security.sh \
  --namespace geoserver-dev \
  --geoserver-release geoserver-cloud \
  --admin-principal you@gov.bc.ca
```

See that script's own header comment for the full rationale, including why
it talks to GeoServer via `oc exec` into a running gateway pod rather than a
tunnel, and the documented curl/`oc exec` `-o /dev/null` quirk on this cluster
that the script works around internally. The script requires `perl` for the
portable whole-file XML update and does not place the admin password in an
`oc exec` argument.

## Install and smoke test

```powershell
bash infra/helm/deploy-geoserver-cloud.sh `
  --namespace geoserver-dev `
  --environment dev `
  --crunchy-release crunchy-postgres `
  --create-namespace

oc get postgrescluster crunchy-postgres -n geoserver-dev
oc get pods,svc,pvc -n geoserver-dev
oc get events -n geoserver-dev --sort-by=.lastTimestamp
```

Confirm the Crunchy PostgresCluster, pgBouncer Service, generated user Secret, and
primary/replica readiness first. Then confirm the proxy and ACL probes, RabbitMQ
readiness, PVC attachment, and the proxy Route or Service. Exercise `/healthz`,
`/auth/login`, and the authenticated GeoServer path through the proxy. Then run
the existing `geoserver-apply validate` and the catalog, ACL, rendering, and
security integration checks against the proxy endpoint.

## Backup, upgrade, and rollback

The default profile uses the Crunchy pgBackRest PVC repository. An off-cluster
S3-compatible repository is optional; when enabled, set
`crunchy.pgBackRest.s3.enabled=true`, configure `bucket`, `endpoint`, and
`secretName`, and provide the referenced Secret through the platform process.
Before a stateful upgrade, execute and verify the approved pgBackRest backup
and restore test. A Helm rollback does not reverse database schema changes.

RabbitMQ's `RABBITMQ_DEFAULT_USER` and `RABBITMQ_DEFAULT_PASS` values are
bootstrap inputs. RabbitMQ ignores them after the data PVC is initialized.
Do not rotate the runtime Secret key by itself, because that changes client
credentials without changing the broker. Perform password rotation as a
maintenance operation against the running broker, verify the new credential,
then update the runtime Secret and restart the application workloads. Record
the procedure with the namespace owner before production use.

For an application-only rollback:

```powershell
helm history geoserver-cloud -n geoserver-dev
helm rollback geoserver-cloud <revision> -n geoserver-dev --wait --timeout 20m
```

Never delete the Crunchy or RabbitMQ PVCs as part of an application rollback.
Restore the database from pgBackRest or use the supported Crunchy downgrade path
for a stateful version rollback.
